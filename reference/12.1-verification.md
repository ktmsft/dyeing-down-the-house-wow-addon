# 12.1 — what still needs reading off the PTR

Everything in this file is a thing the addon currently **assumes**. Each one is
marked in the source too, so nothing here is the only record of it. The rule in
`Data.lua` has always been that an ID is read from the game or it doesn't ship, and
12.1 is PTR-only, so this is the list of what's outstanding rather than a pile of
quiet guesses.

Run `/dye probe` in the PTR client. It opens a window you can select and copy out of.

> **Deploying to the PTR: regenerate the dev loader.** `DyeingDownTheHouseDev.toc`
> is gitignored, so `git fetch` + `reset --hard` does NOT update it — a deploy
> silently keeps whatever file list was there before, and any newly added file
> never loads. That cost a debugging round: `Discover.lua` and `Crafting.lua` had
> been "deployed" for hours without ever running, and the addon looked like it was
> simply ignoring them. Run `tools/make-dev-toc.ps1` in the PTR folder after every
> reset, and if a new file seems to do nothing, check the loader's file list first.


**Most of this list is now answered by the game itself.** 12.1 ships `C_DyeColor`,
and `Discover.lua` reads it at login:

```
C_DyeColor.GetAllDyeColors()        -> every shade's dyeColorID
C_DyeColor.GetDyeColorInfo(colorID) -> { ID, name, itemID, numOwned, ... }
```

A shade's `itemID` is the dye item it costs, so grouping shades by item gives the
nine families, their item IDs and the shade to family map in one pass. Sections 1,
3 and 5 below are resolved by that. Section 2 was confirmed at a station. Only
section 4 — the herb to colour map — is worth a spot-check. Everything else is
answered.

## 1. The nine item IDs — RESOLVED at runtime

`ns.DYES` in `Data.lua` ships with `id = nil` for all nine. Counting still works
(Core matches on the exact item name and learns the ID the first time one lands in
a bag), but nothing counts a dye you've never held, and pricing can't reference one.

`Discover.lua` learns all nine from `C_DyeColor` at login, so they no longer need
to be written into `Data.lua` at all — and shouldn't be, since a hand-copied ID is
a second source of truth that can drift from the live one.

`/dye probe items` still exists and still walks bags, bank, Warband and the mail.
It is now a cross-check rather than the route in: if it and discovery disagree
about an ID, something is wrong and worth knowing about.

## 2. How many herbs make one dye — CONFIRMED

`ns.HERBS_PER_DYE = 10`. Checked at a Dye Station on the PTR, 10 August 2026.

Blizzard never stated a ratio anywhere, so this was carried over from the old
two-step chain on the reasoning that they described the change as removing the
middle step rather than repricing it. That reading was right — but it was a
reading, and every Makeable, Cost and "flowers still short" figure in the addon is
derived from it, so it mattered more than any other single number here.

## 3. Shade families — RESOLVED, and the guesses were the safe part

Read from `C_DyeColor` on 12.1, 10 August 2026, via `/dye probe shades`. All 77
confirmed, nothing left carrying `guess = true`, and `Data.lua` corrected.

**Eight of the 77 were wrong. Only one of them was a shade I had flagged.**

The nine guesses scored 8 out of 9 — every one of the four ex-teal shades landed
exactly where the reasoning said. "Teal split between blue and green" held.

| guessed | verdict |
|---|---|
| Kul Tiran Steel → blue | right |
| Tidesage Teal → blue | right |
| Vortex Teal → blue | right |
| Un'Goro Green → green | right |
| Aethril Pink → purple | right |
| Faded Mana → purple | right |
| Stonetalon Brick → red | right |
| Petal Pink → red | right |
| Klaxxi Amber → yellow | **wrong — orange** |

Worth pinning down, because it is the same trap section 4 fell into: teal→blue was
right for the *shades* and wrong for the *herbs*. The shades did move to blue and
green; the herbs that used to feed teal did not follow them. Two different questions
that read as one.

**The seven that were never guesses.** These came off the old dyes' pigments — the
part of `Data.lua` described in its own header as "solid, it was read off the
recipes themselves" — and had been wrong since before 12.1:

| shade | shipped | actually |
|---|---|---|
| Ironclaw | black | green |
| Stormsteel | black | blue |
| Dusk Lily Grey | blue | purple |
| Dark Gold | brown | yellow |
| Vol'dun Taupe | brown | green |
| Holy Oak Tan | yellow | white |
| Pinewood | yellow | green |

Read them and they are obvious: pinewood *is* green, a taupe is nearer green than
brown, holy oak is pale. They read as safe because the name suggested a family and
the old data agreed, so nobody looked.

**The lesson is about the flag, not the data.** `guess = true` was meant to mark
what needed checking. What it actually did was make everything *without* it look
verified — so the nine flagged entries got a probe written for them and scored 8/9,
while the 68 unflagged ones went unexamined and scored 61/68. A confidence marker on
some rows is a confidence claim about all the others.

Misfiling a shade only mislabels a reference row and moves where a goal is counted;
it never miscounts a dye. So this was cheap to be wrong about — unlike section 4.

The test suite now asserts the guess count is **0**, and pins the eight corrected
placements by name so a reordering can't silently revert them.

## 4. The herb → color map — RESOLVED, and it was wrong

Read at a Dye Station on the 12.1 PTR, 10 August 2026. **17 flowers per color,
except blue and green with 18.** `Discover.lua` now re-reads it at every station
visit, so `Data.lua` is the fallback rather than the answer — but it has been
corrected to match what the station said.

**The teal fold was wrong, and it was the expensive kind of wrong.** The groupings
were carried over from the pigment each herb milled into, on the reasoning that
removing the middle step doesn't change which herbs are which color. That part held
— seven of the nine colors came back byte-identical. What did not hold was the
exception bolted onto it: that every herb which fed teal now feeds **blue**, because
the teal pigment itself converted to Blue Housing Dye.

An ex-teal herb dropped teal and kept whatever else it already had. Lichbloom is
black, Hochenblume is purple, Marrowroot is brown, Orbinid is purple. Bruiseweed was
teal-only, so the fold had nowhere to put it but blue — the station says **green**.

Thirteen herbs, and blue was carrying every one: **31 flowers against a real 18**.
That is not a misfiled reference row. Makeable, Cost and "flowers still short" are
all summed over a color's herb list, so blue had been claiming dyes that could not
be made — the one class of error this addon's house rule about under-reporting
exists to avoid.

| | shipped | station |
|---|---|---|
| blue | 31 | 18 |
| green | 17 | 18 |
| the other seven | 17 each | identical |

**The tell was a coincidence.** Tranquility Bloom — a teal/white herb, and 12.1's
new blue is called Tranquility Blue — is white only. The names rhymed and the
inference was still wrong. An item conversion said nothing about the herbs feeding
it, and one piece of corroboration was enough to make a guess feel like a finding.
That is the argument for `/dye probe herbs` over another round of reasoning.

### The shape it had to be read through

The dye recipes are **salvage recipes** — `isSalvageRecipe = true`, the Milling
shape: one slot that accepts any of seventeen flowers, ten at a time. Which is a
better model of what a dye is than an ordinary craft, and means the flower list is
**not in the schematic's reagents**. `reagentSlotSchematics` comes back with no
reagents at all; the accepted items are served separately:

```
C_TradeSkillUI.GetSalvagableItemIDs(recipeID) -> { itemID, ... }
```

(Blizzard's spelling: "Salvagable". `Discover.lua` tries both.)

The first version of the reader assumed ordinary reagents, read nothing, and
reported "no dye recipes in this window" — indistinguishable from standing at the
wrong window. `ns.ReadStationHerbMap` now returns "the API answered" separately from
"there were dyes in it", and the probe lists the recipes it found **and rejected**,
so the next failure of this kind says which link broke.

Recipe IDs, for reference: Black 1306642, Purple 1306629, Blue 1306796, Brown
1306797, Green 1306799, Orange 1306801, Red 1306802, White 1306803, Yellow 1306804.
All under `categoryID 2670` / `skillLineID 2984`, named "Dye Crafting".

### One craft, one dye — and a near miss

The dye recipes have **no reagent slots at all**, so `quantityRequired` is never
served. The count lives on the schematic as `quantityMin` / `quantityMax`, which
both read **10** on all nine.

Those two fields name the OUTPUT on an ordinary craft, and the first version of the
probe read them that way: it reported that a craft makes ten dyes and that Makeable
had been understating tenfold. **It isn't and it wasn't.** Ten is what the craft
*eats*:

- the recipe's own description reads "Create **one** Purple Housing Dye";
- the station's reagent line reads `24/10 Silverleaf`;
- 10 is exactly the input requirement counted by hand in section 2.

A salvage recipe consumes a quantity and produces loot; that is the shape being
described. Acting on the probe's first verdict would have multiplied every Makeable,
Cost and short figure by ten — a worse number than the blue overcount this whole
exercise set out to remove, and arrived at the same way: a field whose name implied
an answer, on a recipe shape that meant something else by it.

So `ns.HERBS_PER_DYE` is now **read** from `quantityMin` rather than hand-counted,
taken only from a salvage recipe that offered no slots. One dye out stays an
assumption, but it is Blizzard's own wording and the input count is the line that
would stop matching if it ever changed.

`hasSingleItemOutput = false` and `canCreateMultiple = true` are consistent with a
salvage recipe and say nothing about the yield.

## 5. The dye panel's frame shape — RESOLVED

`DecorCustomizationsPane` never moved. 12.1 pushed a `CustomizeComponentContainer`
underneath it and moved every dye field down into a `DyePane` inside that:

```
HouseEditorFrame.activeModeFrame.DecorCustomizationsPane
  .CustomizeComponentContainer.DyePane
    .DyeCostContainer          39x16
    .dyeSlotFramesByChannel
    .DyeSlotContainer          children carry .dyeSlotInfo and .CurrentSwatch
    :GetPreviewDyeInfos()
```

That shape is why it read as an addon bug: the old path still resolves perfectly
and everything it held is one layer further down.

`currentChannel` is gone with no obvious replacement, so `CurrentDye` walks every
slot and takes the first holding a dye rather than guessing at a successor field.

**`dyeColorCategoryID` is NOT one of the nine families**, though it looks like it
might be. `C_DyeColor.GetAllDyeColorCategories()` returns `{1, 2, 3}` and category 1
is named "General"; Warm Teak reports `dyeColorCategoryID = 0`. Wiring goals to it
would put every count against the wrong colour.

A better route exists anyway and needs no frames at all:
`C_HousingCustomizeMode.GetSelectedDecorInfo()` returns the decor's `dyeSlots`, each
with `dyeColorID` and `dyeColorName`. Worth moving to.

## 6. The Dye Station UI — RESOLVED, and a lesson

`Crafting.lua` was deleted earlier in this release and is back, because the premise
it was deleted on was wrong.

Blizzard's post says "there are no recipes in your own crafting book to manage",
which I read as the crafting UI being gone. It isn't. The recipes moved out of your
profession book and into the station, which opens an ordinary Professions-style
window titled **Dye Crafting** with nine recipes in it, one per colour, reagents
shown as `24/10 Silverleaf`, and Create / Create All buttons.

**The lesson is the reading.** The sentence described where the recipes live, not
whether a window exists, and a feature was deleted on prose rather than on a look
at the client. `/dye probe station` now exists so the shape is checked rather than
assumed — the same mistake in the other direction is what cost the housing panel
earlier in this same release.

That window also independently confirms section 2: the reagent line reads `/10`.
